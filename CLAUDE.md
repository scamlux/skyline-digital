## 1. Что строим

Сайт-портфолио и одновременно точка приёма заказов для веб-студии одного человека (Ташкент, Узбекистан). Три функции:

1. **Портфолио** — каталог моих проектов с динамическими детальными страницами.
2. **Витрина услуг** — что можно заказать и как формируется цена.
3. **ИИ-калькулятор смет** — клиент проходит форму, получает персональную страницу со сметой и скачивает коммерческое предложение (PDF) в фирменном шаблоне.

Плюс **админка**, где я добавляю проекты и правлю прайс без деплоя.

## 2. Стек — не обсуждается

- Next.js 15, App Router, TypeScript strict, React Server Components по умолчанию
- Tailwind CSS v4 + CSS-переменные для токенов
- Supabase: Postgres + Storage + Auth (только для админки), доступ через `@supabase/ssr`
- Анимации: Framer Motion (интерфейс) + React Three Fiber / drei (3D-сцены)
- Формы: React Hook Form + Zod
- i18n: next-intl, локали `ru` (default) / `en` / `uz`, префикс в URL
- PDF: рендер HTML-шаблона в PDF на сервере (`@react-pdf/renderer`, либо Playwright+Chromium если нужна пиксельная точность — выбери сам, обоснуй в ADR)
- ИИ: Anthropic Messages API, модель `claude-sonnet-4-6`
- Деплой: Vercel
- Пакетный менеджер: pnpm. Линт: ESLint + Prettier. Тесты: Vitest (юниты движка цен) + Playwright (e2e критичных путей)

## 3. Дизайн

Источник — файл Figma «wolf (Copy)»: `https://www.figma.com/design/29mWxkkVv2mzL86sYFY0rD/wolf--Copy-`

Порядок работы с ним:

1. Вытяни через Figma MCP переменные, цвета, типографику, сетку и компоненты. Собери из них `src/styles/tokens.css` и Tailwind-конфиг. **Никаких хардкод-значений цвета и отступов в компонентах** — только токены.
2. Макет неполный. Экраны, которых в нём нет (калькулятор, страница сметы, админка), достраивай **в той же системе**: те же токены, та же сетка, та же плотность, та же логика скруглений и теней. Не изобретай второй визуальный язык.
3. Если Figma MCP не отдаёт файл (нет прав) — не блокируйся: работай по скриншотам из `design/` и оставь `docs/DESIGN-GAPS.md` со списком того, что пришлось додумать.

**3D и анимация — обязательная часть, а не украшение.** Заказчику это нравится и это отличает сайт. Требования:

- Хотя бы одна крупная 3D-сцена в hero главной, реагирующая на курсор/скролл.
- 3D-акценты на карточках услуг и в переходах между шагами калькулятора.
- Всё ленивое: `dynamic(() => ..., { ssr: false })`, canvas грузится после первого paint, вес сцены ≤ 400 КБ.
- `prefers-reduced-motion` уважается всегда — есть статичный фолбэк.
- На мобильных 3D упрощается или заменяется на видео/постер. LCP ≤ 2.5 с на 4G — это жёсткая граница, красивая сцена, которая роняет метрику, считается несделанной задачей.

## 5. Каталог проектов — как он работает

Это моё портфолио, и добавлять проекты я должен быстро, не переписывая по три абзаца текста руками.

**Сценарий добавления в админке:**

1. Я жму «Новый проект» и даю минимум: название, ссылка на живой сайт (или скриншоты), тип услуги, стек, год, 2–3 факта о результате.
2. Жму «Заполнить с ИИ». Модель забирает то, что я дал (если есть URL — читает страницу), и **предзаполняет поля**: краткое описание для превью (до 140 знаков), задача, решение, результат, теги, SEO-title и description, alt-тексты. Всё это на трёх языках.
3. Я правлю руками что не нравится и жму «Опубликовать».

**Критично:** ИИ заполняет поля формы, которые я вижу и могу отредактировать. Он ничего не публикует сам. Каждое сгенерированное поле помечено бейджем «ИИ» до первого ручного редактирования.

**Превью в каталоге и на главной** берётся из тех же полей: обложка, название, краткое описание, теги, год. Одна карточка — один компонент, используется и на `/work`, и на главной.

**Детальная страница** `/work/[slug]` — динамическая, генерится из данных, а не хардкодится:

- Hero: обложка, название, клиент, год, роль, стек, ссылка на живой сайт
- Блок цифр (метрики результата)
- Задача → Решение → Результат
- Галерея (изображения и видео, лайтбокс)
- Технологии
- Следующий/предыдущий проект
- CTA «Хочу так же» → ведёт в калькулятор с предвыбранным типом услуги

Рендер: `generateStaticParams` + ISR `revalidate: 60`. Черновики видны только авторизованному админу.

RLS включён везде. Публично читаемы: `services`, `service_options` (active), `projects` (published). `estimates` читается только по точному `token`. Всё остальное — только для роли admin.

Каждая смета хранит `price_snapshot` — копию прайса на момент расчёта. Изменение цен не должно менять уже выданные клиентам сметы.

## 7. Движок цен

**Железное правило: сумму считает код, модель — никогда.** Модель может _предложить_ добавить позицию, и тогда позиция показывается отдельным блоком «рекомендуем добавить» с отдельной ценой из прайса. Модель не пишет и не изменяет ни одной цифры в смете.

Формула:

```
base        = service.base_price_usd
options     = Σ fixed + Σ (base × percent) + Σ (per_unit × количество)
subtotal    = base + options
urgency     = subtotal × (срочно ? 0.35 : 0)
total       = subtotal + urgency
range       = [total × 0.9, total × 1.15]     // показываем вилкой
weeks       = ceil((base_days + Σ days_delta) / 5), вилка ±1 неделя
```

Валюта: базовая USD, дублируем в UZS по курсу из `settings.fx_rate` (стартовое значение 12 000, редактируется в админке).

## 8. ИИ-слой — что модели можно, а что нельзя

Ключ живёт **только** в `ANTHROPIC_API_KEY` на сервере. Ни в клиентском бандле, ни в репозитории, ни в примерах — нигде. `.env.example` содержит имена переменных без значений.

Три места, где работает модель:

**А. Разбор описания проекта в калькуляторе.** Вход: свободный текст клиента + выбранные ответы. Выход строго по JSON-схеме (tool use / structured output): `understood_scope`, `suggested_option_keys[]` (только ключи из прайса, ничего вне списка), `clarifying_questions[]`, `risk_flags[]`. Цифр в выходе нет.

**Б. Текст коммерческого предложения.** Вход: посчитанная смета (позиции, суммы, недели) + профиль клиента. Выход: `summary`, `understanding`, `scope_in[]`, `scope_out[]`, `stages[]`, `assumptions[]`, `why_us`, `next_step`. Суммы приходят как готовые строки и **вставляются как есть** — модели запрещено их пересчитывать, это фиксируется в системном промпте и проверяется валидатором после ответа.

**В. Предзаполнение карточки проекта в админке.** Описано в разделе 5.

Общие правила: таймаут 30 с, ретрай с бэкоффом, при провале — фолбэк на шаблонный текст, чтобы смета выдалась всё равно. Каждый вызов логируется в `ai_calls` (модель, токены, латентность, стоимость) — я хочу видеть, во что мне это обходится.

## 9. Шаблон КП — эталон

В `reference/` лежит мой реальный КП («КП — Сайт TGPG.UZ»). **Это эталон, воспроизводи его структуру и типографику.** Разобранные параметры:

- Формат 16:9, фон белый, шрифт Arial (в вебе — системный аналог)
- Цвета: чернила `#1A1A1A`, синий акцент `#0B4EA2` и `#1155CC`, серый текст `#6B7480`, светло-серый `#9AA3AE`, красный акцент `#C8392B`, кремовый `#FFE4CC`
- Номер страницы справа внизу, логотип слева внизу — на каждом слайде
- Слева описание, справа изображение/диаграмма — устойчивый паттерн

Структура из 8 полос:

1. **Обложка** — «Коммерческое предложение для разработки: НАЗВАНИЕ», клиент, автор, город, год
2. **Инфраструктурная диаграмма** — как устроен сайт, где данные, куда уходят заявки
3. **Дизайн** — превью макета
4. **Бизнес-процесс** — путь клиента, шаги
5. **От клиента ждём** — чек-лист с статусами «сделано / не сделано»
6. **Этапы разработки** — колонки по неделям
7. **Сумма проекта** — таблица «сотрудник · количество · месяц · ставка · сумма» со справочной рыночной оценкой, затем блок **ВАША ЦЕНА** с суммой в USD и UZS и процентом выгоды
8. **График оплаты** — предоплата / после запуска, итог, стоимость со второго года, цена правок, контакты

Слайд 7 — коммерческое ядро документа: сначала показывается, сколько это стоило бы командой из шести человек по ставкам Ташкента, потом моя цена и разница в процентах. Этот приём обязателен, движок должен уметь считать «рыночную» оценку по таблице ставок из раздела 7 и выводить дельту.

Генерируем на выходе PDF. Он же сохраняется в Supabase Storage и прикладывается к письму.

## 10. Как ты работаешь

1. **Сначала план.** Заведи `TODO.md` со списком задач по фазам, помечай статусы. Обновляй его по ходу — это моё окно в твою работу.
2. **Мелкими коммитами.** Один коммит — одна законченная мысль. Осмысленные сообщения на русском или английском, но последовательно.
3. **Ветка на фазу**, PR в `main`, в описании — что сделано и что проверено.
4. **Задача не закрыта, пока не проходит:** `pnpm typecheck && pnpm lint && pnpm build && pnpm test`. Красный билд — задача в работе, а не «сделано с замечанием».
5. **Проверяй глазами.** Для каждого готового экрана снимай скриншот через Playwright в 1440px и 390px, смотри на него сам и сравнивай с макетом. Кладите в `screenshots/`. Не показывай мне «готово», не посмотрев на результат.
6. **ADR на развилках.** Каждое неочевидное техническое решение — короткая запись в `docs/adr/NNN-название.md`: контекст, варианты, выбор, последствия. Три-четыре абзаца, не диссертация.
7. **Сиды и фикстуры.** База должна подниматься с нуля одной командой и наполняться демо-данными: 6 услуг, 12 опций, 6 проектов-заглушек. Я должен увидеть живой сайт, не заводя контент руками.
8. **Не оставляй заглушек молча.** Если что-то замокано — строка в `docs/DESIGN-GAPS.md` или `TODO.md`, а не тихий `// TODO` в глубине файла.

## 11. Безопасность — проверяй перед каждым PR

- Секреты только в env. `.env*` в `.gitignore`. В репозитории — ни одного ключа, включая примеры и комментарии.
- RLS включён на всех таблицах, проверено запросом от анонимной роли.
- Публичные ИИ-роуты за rate limit (по IP и по сессии) + капча на последнем шаге формы. Без этого мой ключ выжигают за ночь.
- Валидация всего входа через Zod на сервере, не только на клиенте.
- Загрузка файлов: белый список типов, лимит размера, отдельный бакет, антивирус-проверка через Supabase.
- Страница сметы доступна по неугадываемому токену (32+ символа), но не индексируется: `noindex` + запрет в `robots.txt`.

## 12. Готовность к запуску

- Lighthouse ≥ 90 по всем четырём метрикам на главной, `/work/[slug]` и `/estimate`
- LCP ≤ 2.5 с, CLS ≤ 0.1 на мобильном 4G
- Все три локали заполнены, ни одного непереведённого ключа
- `sitemap.xml`, `robots.txt`, OG-картинки генерируются динамически, JSON-LD для проектов и услуг
- Работает на iOS Safari и Android Chrome — проверено, а не предположено
- Формы валидируются, ошибки на языке пользователя, состояния загрузки везде есть
- Клавиатурная навигация и фокус-стили работают; контраст проходит WCAG AA

## 13. Когда останавливаться и спрашивать

Не спрашивай про архитектуру, именование, библиотеки, структуру папок, порядок задач — решай сам. Останавливайся и пиши мне только если:

- нужен доступ, которого нет (Figma, домен, платный сервис);
- задача требует потратить мои деньги (платный тариф, покупка домена, лимиты API);
- нашёл в требованиях противоречие, которое нельзя разрешить в пользу очевидного варианта;
- нужно удалить или необратимо изменить данные;
- три подряд попытки починить одно и то же провалились — не долби, опиши что пробовал.

Во всех остальных случаях: выбери разумный вариант, запиши выбор в ADR и иди дальше.
