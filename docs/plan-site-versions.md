# План-промпт · Версии сайта (Studio + Референс) с переключателем из админки

> Этот документ — одновременно план и промпт для сессии-исполнителя. Он описывает,
> как перенести из артефакта-прототипа два **новых** варианта главной страницы
> (**Studio** и **Референс**) в реальный проект Skyline Digital и дать мне
> переключать активный вариант из админки — **не трогая текущий («старый») дизайн**.
> Прототип: артефакт `claude.ai/artifact/3sa6opoSTEwRxMNrTxbesp` (три версии + эффекты).

> **Спутники:** `docs/reference/artifact-skyline.html` — пиксельный эталон

## 1. Жёсткие ограничения (требования заказчика)

1. **Старый дизайн не трогаем.** `src/app/[locale]/page.tsx` и его компоненты/токены
   остаются как есть. Вариант `old` = «рендерить то, что есть сейчас», без рефакторинга
   «под артефакт». Никаких правок визуала старой версии.
2. **Делаем только Studio и Референс** как два новых варианта. Их верстаем с нуля в
   реальных компонентах (порт из артефакта), на реальных данных, i18n и 3D — не копируем
   один гигантский HTML, а раскладываем на RSC + клиентские острова.
3. **Переключатель из админки + реальная реализация.** Активный вариант задаётся
   настройкой `site_version ∈ {"old","studio","ref"}`; публичный сайт рендерит выбранное.
   Значение меняется из `/admin/settings` одним кликом (сегментированный переключатель).

## 2. Ключевое архитектурное решение

**Настройка-селектор + пострановые диспетчеры + вариантный каркас.** Охват —
**весь публичный сайт** (решение заказчика). Каждая публичная страница становится тонким
диспетчером: читает `site_version` и рендерит свой вариант. Каркас (Header/Footer/курсор/
preloader/тема) тоже вариантный.

```
src/app/[locale]/page.tsx             ← диспетчер главной
src/app/[locale]/projects/page.tsx    ← диспетчер каталога
src/app/[locale]/projects/[slug]/…    ← диспетчер детальной
src/app/[locale]/services/…           ← диспетчеры услуг
src/app/[locale]/about|contact|calculator|estimate/…  ← диспетчеры
src/components/site/
  variants.ts                         ← общий тип SiteVersion + getActiveVersion() (кэш-тег)
  chrome/{OldChrome,StudioChrome,RefChrome}.tsx  ← Header/Footer/курсор/preloader варианта
src/components/<page>/variants/
  Old<Page>.tsx                       ← ВЫНОС текущего содержимого страницы (1:1, без правок)
  studio/Studio<Page>.tsx             ← новый Studio (RSC + острова)
  ref/Ref<Page>.tsx                   ← новый Референс (RSC + острова)
  index.ts                            ← реестр { old, studio, ref }
```

Диспетчер страницы (эскиз, одинаков для всех):

```tsx
const version = await getSetting<SiteVersion>("site_version", "old"); // дефолт = старый
const Variant = PAGE_VARIANTS[version] ?? PAGE_VARIANTS.old;          // фолбэк на старую
return <Variant locale={locale} … />;
```

**Каркас** (`[locale]/layout.tsx`) тоже читает `site_version`, ставит `data-site`,
подключает Onest+акцент и вариантный Header/Footer/курсор/preloader. Для `old` — текущие
Header/Footer/токены без изменений.

**Почему так:** старый код каждой страницы переезжает в `Old<Page>.tsx` дословно
(вырезать/вставить, те же импорты) — визуально ничего не меняется. Новые варианты не
пересекаются со старым ни файлами, ни токенами.

**Поведение при раскатке (никогда не «наполовину сломано»):** страница, у которой вариант
Studio/Референс ещё не собран, отдаёт **свою `old`-версию целиком (вместе со старым каркасом)**
при любом `site_version`. То есть переключатель влияет только на уже портированные страницы;
каждая страница внутри себя консистентна (единый каркас+тело). По мере раскатки фолбэков
становится меньше. Это осознанный компромисс ради работоспособности на всех этапах —
зафиксировать в ADR.

### Кэш/ISR — обязательный нюанс
Сейчас главная статична. Чтобы смена настройки отражалась у посетителей:
- в `saveSetting` при ключе `site_version` вызывать `revalidateTag("site-settings")`
  (или `revalidatePath("/", "layout")`), а `getSetting` пометить
  `unstable_cache(..., { tags: ["site-settings"] })`;
- фолбэк, если тегами не захотим: на главной `export const dynamic = "force-dynamic"`
  (проще, но теряем ISR — зафиксировать выбор в ADR).
Выбор закэшировать по `site_version`, не по локали.

## 3. Модель данных

Новая миграция `supabase/migrations/0013_site_version.sql`:

```sql
insert into public.settings (key, value) values
  ('site_version', '"old"'::jsonb),      -- активный вариант
  ('brand_accent', '"dark-blue"'::jsonb) -- основной цвет новых вариантов
on conflict (key) do nothing;            -- RLS уже включён, политик не добавляем
```

Значения — JSON-строки, читаются существующим `getSetting`:
`site_version ∈ "old"|"studio"|"ref"`, `brand_accent ∈ "dark-blue"|"burgundy"|"khaki"|"dark-green"|"brass"`.
Больше ничего в БД не нужно: варианты берут контент из тех же `projects`/`settings`/i18n.

## 4. Админка — переключатель

- Новый клиентский компонент `src/app/admin/settings/SiteVersionSwitcher.tsx`:
  сегментированные кнопки **Старый / Studio / Референс**, активная подсвечена; клик →
  `saveSetting("site_version", JSON.stringify(value))` в `useTransition`, тост «Сохранено».
- Рядом — второй сегментированный переключатель **Акцент бренда** (5 образцов цвета
  → `saveSetting("brand_accent", …)`), меняет основной цвет новых вариантов (см. §5).
- Отрисовать оба сверху `src/app/admin/settings/page.tsx` (над общим key-value редактором;
  сырой редактор оставляем). Текущие значения читаем там же из `settings`.
- Авторизацию админки не ослабляем — используем существующий гейт (middleware/layout).
- **(Опц., Фаза 2) Превью без переключения для всех:** `?__ver=studio` на главной,
  разрешён только при админ-куке/preview-режиме, страница с `noindex`. Публичного
  тумблера «как в артефакте» на боевом сайте **не делаем** — вариант выбирает только админ.

## 5. Токены и шрифты (изоляция вариантов)

Старые токены (night/apricot) не трогаем. Для новых вариантов — **скоуп по обёртке**,
чтобы стили не текли в старый дизайн:

- Обёртки: `<div data-site="studio">…</div>`, `<div data-site="ref">…</div>`.
- Переменные вариантов объявляем под скоупом: `[data-site="studio"]{ --s-bg:…; --s-ink:… }`,
  `[data-site="ref"]{ --r-bg:#07070a; --acc:…; … }`. **Никаких хардкод-цветов в JSX** —
  только переменные (CLAUDE.md §3).
### Акцент бренда = основной цвет темы (не хайлайт)
Отдельная настройка `brand_accent ∈ {dark-blue, burgundy, khaki, dark-green, brass}` (jsonb),
переключается теми же сегментами в админке. **Акцент меняет основной цвет варианта, и от него
перекрашивается почти всё видимое**, а не один мелкий элемент:

- Единый источник — переменные `--acc` (основной цвет) и `--acc-ink` (контрастный текст на нём),
  плюс производные (`--acc-weak`, `--acc-strong`, `--acc-glow`), вычисленные от `--acc`
  (`color-mix(in oklch, …)`), чтобы не держать пять ручных палитр.
- От них зависят: **кнопки** (фон/бордер/текст, hover/active/focus-ring), **ссылки и
  акцентный текст**, **эффекты** (свечения, градиенты, тени, подсветка активной секции,
  прогресс-бары), **3D-акценты/подсветка**, **кастомный курсор**, **бордеры на акценте**,
  `::selection`, индикаторы в карусели и меню. Правило: любой «цветной» (не нейтральный)
  элемент берёт цвет из `--acc*`, нейтральные (фон/текст-основной/линии) — из токенов варианта.
- Применяется ко **всем трём** значениям вне зависимости от выбранного `site_version`
  (и Studio, и Референс читают `--acc`), независимо от переключателя версии.
- **Старого дизайна не касается** — переменные акцента объявляются только под
  `[data-site="studio"]` / `[data-site="ref"]`.
- Если под отдельный акцент захочется ещё и свой типографический/эффект-пресет (не только
  цвет) — оформляем как пер-акцент пресет (мапа `accent → { font?, effectVars }` на обёртке);
  по умолчанию акцент меняет цветовую систему, шрифт остаётся Onest.
- **Шрифт Onest** (единый для новых вариантов, кириллица подтверждена) — через next/font,
  переменная `--font-onest`, навешивается **только на обёртку варианта**, а не на `<html>`,
  чтобы не грузиться на старой версии. Стили вариантов используют `--font-onest`.
- Файлы стилей вариантов: `src/components/home/variants/studio/studio.css` и `ref/ref.css`,
  импортируются только их компонентами. (Либо Tailwind-утилиты под `data-site`-скоупом —
  выбрать в ADR; главное — изоляция.)

## 6. Studio-вариант (`studio/StudioHome.tsx`)

Светлый современный дизайн из артефакта, на реальных данных/i18n. Секции (порт 1:1 по
логике, но компонентами):

1. **Hero** — параллакс-силуэт города, восход; крупный заголовок на Onest. 3D/параллакс —
   ленивый клиентский остров (`dynamic(..., { ssr:false })`), статичный постер-фолбэк.
2. **Услуги** — анимированный список (из `SERVICE_KEYS` + i18n `services.items.*`,
   цены из `basePriceUsd`). Эффект появления строк, 3D-акцент.
3. **Проекты** — горизонтальная карусель-скролл (из `getProjects()`), качественные превью
   (`PreviewCard`/оптимизированные обложки), клик → `/projects/[slug]`.
4. **Процесс** — скролл-прогресс со сменой шагов.
5. **Стек / О себе / Калькулятор-CTA / Финальный CTA** — реальные ссылки (`/calculator`,
   `/projects`, `/about`, `/contact`), тексты из `messages`.

Клиентские острова помечаем `"use client"` и грузим лениво; статическую структуру держим в RSC.

## 7. Референс-вариант (`ref/RefHome.tsx`) — сигнатурные эффекты

Award-style тёмная версия «как на референсах». **Каждый компонент и модалка — в этом языке.**
Плавность — приоритет (`cubic-bezier`, rAF, `easeInOutCubic`). Переносим из артефакта:

- **Preloader** со счётчиком % и кнопкой «Пропустить».
- **Кастомный курсор** (точка + лерп-кольцо, `mix-blend-mode:difference`) — только десктоп,
  только внутри `data-site="ref"`.
- **Кинетический hero** с ротатором слов (не сдвигает соседний текст).
- **Полноэкранное меню-модалка.**
- **Индекс проектов** со строками и плавающим hover-превью.
- **Depth-переход «Философия»** — sticky scroll-scale (карточка → фуллскрин, blur/radius→0).
- **Depth-открытие кейса из кликнутой строки (FLIP)** — уже отлажено в артефакте: клик по
  строке запоминает `getBoundingClientRect()`, медиа «вырастает» из позиции строки в фуллскрин
  (`transform-origin:0 0; translate()+scale()` → `scale(1)`), закрытие — обратно; есть
  `prefers-reduced-motion`-фолбэк. **Порт этой логики в клиентский компонент `RefProjectIndex`.**
- **«Что мы делаем»** — pinned horizontal scroll (вертикальный скролл двигает горизонталь,
  поэтапные панели).
- Кейсы наполняем из `getProjects()` (не хардкодим), ссылки «Открыть сайт» — `project.url`.

Важно (CLAUDE.md §3): sticky-эффекты ломает `overflow:hidden` на родителе — в артефакте это
был баг, на обёртке варианта `overflow` не ставить (горизонтальный скролл гасим точечно).

## 8. i18n

- Новых текстов-заглушек не плодить: Studio и Референс берут те же ключи `home.*`,
  `services.*`, `projects.*`. Если варианту нужен уникальный текст (слоганы ротатора,

  сразу** (`ru`/`en`/`uz`), без непереведённых ключей (CLAUDE.md §12).
- Контент фактический, без выдуманных кейсов/клиентов/цифр (CLAUDE.md исходный).

## 9. 3D и производительность

- 3D — обязательная часть (CLAUDE.md §3): R3F / drei, ленивая загрузка после первого paint,
  вес сцены ≤ 400 КБ, canvas только в клиентском острове с `ssr:false`.
- `prefers-reduced-motion` уважается во всех вариантах — статичные фолбэки (preloader,
  курсор, параллакс, depth, карусель).
- Мобильный: 3D упрощается/заменяется постером. **LCP ≤ 2.5 с на 4G** — жёсткая граница;
  красивая сцена, роняющая метрику, = задача не сделана.
- Lighthouse ≥ 90 по всем метрикам на главной в активном Studio и в активном Референс.

## 11. Фазы и ворота

Охват — весь сайт, поэтому раскатываем **пострановно**: для каждой страницы делаем сразу
оба новых варианта (Studio и Референс), затем переходим к следующей. Так сайт на каждом
этапе рабочий (непортированные страницы — на фолбэке `old`, см. §2).

**Фаза 0 — каркас и инфраструктура (без визуальных изменений для посетителя).**
- `SiteVersion` + `getActiveVersion()` (кэш-тег), вариантный каркас `chrome/*`, пострановый
  паттерн-диспетчер, миграция `0013` (дефолт `old` + `brand_accent`), ревалидация при смене.
  Вынести главную в `OldHome` (1:1). ADR `docs/adr/0013-site-version-switch.md`.
- Переключатели версии и акцента в админке (рабочие).
- Гейты зелёные. Внешне сайт идентичен текущему — проверить скриншотом.

**Фаза 1 — Главная (Studio + Референс).**
- `StudioHome` (§6) и `RefHome` + все эффекты (§7: FLIP-открытие кейса, pinned horizontal,
  preloader, курсор, меню-модалка, depth-«Философия»). Вариантный Header/Footer.
- Скриншоты 1440/390 обоих вариантов × ключевые акценты, reduced-motion, мобилка,
  Lighthouse/LCP. Гейты.

**Фаза 2 — Каталог и детальная проекта** (`/projects`, `/projects/[slug]`).
**Фаза 3 — Услуги** (`/services`, `/services/[slug]`).
**Фаза 4 — О себе / Контакты** (`/about`, `/contact`).
**Фаза 5 — Калькулятор и смета** (`/calculator`, `/estimate/[token]`).
- В каждой фазе: Studio + Референс варианты страницы в вариантном каркасе, реальные данные/i18n,
  3D-акценты по месту, акцент бренда прокинут, reduced-motion/мобилка, скриншоты 1440/390,
  Lighthouse/LCP, гейты. Пока фаза не сделана — страница на фолбэке `old`.

**Фаза 6 — финал.**
- (Опц.) превью `?__ver=` / `?__accent=` под админ-кукой, `noindex`. Прогон всех трёх версий
  × пяти акцентов по всем страницам. `docs/DESIGN-GAPS.md` по тому, что пришлось додумать.
  Draft-PR в `main` с описанием и чек-листом проверок.

> Фазы 1–5 можно вести отдельными PR-ами (ветка на фазу), чтобы ревью было обозримым.

**Ворота перед каждым коммитом/PR:** `pnpm typecheck && pnpm lint && pnpm build && pnpm test`
зелёные; для готового экрана — скриншот, который сам посмотрел; неочевидные развилки — ADR.
Мелкими осмысленными коммитами, ветка `claude/gracious-dirac-vx3pie`.

## 12. Границы (чего НЕ делаем)

- Не меняем старый дизайн и его токены/компоненты/тексты.
- Не делаем вариант `old` «как в артефакте» — это ровно текущий боевой код.
- Публичного тумблера версий на боевом сайте нет — выбор только из админки.
- Охват — **весь сайт** (решение заказчика), раскатка пострановно (§11). Непортированная
  страница держится на фолбэке `old` целиком, пока её вариант не готов — промежуточных
  «полусломанных» состояний нет.
