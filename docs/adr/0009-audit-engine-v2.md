# ADR 0009 — Движок аудита v2: SSRF-guard в браузере, ожидание DOMContentLoaded

**Статус:** принято · 2026-10-26

## Контекст

Прогон движка v1 по 150 случайным сайтам радара (`docs/business/AUDIT-STARTUP-RESEARCH-2026-10.md`) показал, что 39% сайтов не оценены, из них 30% — `TIMEOUT`. Разбор десяти таймаутов по одному выявил три причины:

- **Предварительная проверка редиректов.** Node-запрос `guardRedirectChain` до запуска браузера занимал 5–20 с, а сайты с защитой от ботов (Booking) его не проходили.
- **Ожидание `load`.** Тяжёлые сторонние виджеты откладывают событие `load` на 20+ с при DOM, готовом за 3–9 с.
- **Мусорные URL в радаре:** несколько адресов через `;`, ссылки на Booking и Google Sites.

Медленный сайт превращался в «недоступен», хотя медлительность и есть главная находка для владельца бизнеса.

## Варианты

1. Поднять лимиты времени. Это дешевле, но предварительная проверка и `load` так и остаются узким местом, и отчёт становится дольше для всех.
2. Перенести SSRF-guard в перехват запросов браузера и ждать `domcontentloaded`, а `load` ждать мягко, в пределах бюджета.
3. Перейти на Lighthouse. Это тяжело для serverless, замер медленнее, и контроль над бюджетом теряется.

## Решение

Вариант 2.

**Защита (SSRF).**
- Входной URL проверяется только по DNS (`guardUrl`) до запуска браузера.
- Каждый запрос браузера проходит через `page.setRequestInterception(true)` и `createRequestGuard`: навигация, каждый хоп редиректа и подресурсы. Проверяются схема, порт и все разрешённые IP. Результат кешируется по хосту в рамках одного аудита.
- `data:` и `blob:` пропускаются.
- `setBypassServiceWorker(true)` — запросы service worker обходят перехват.
- Каждый перехваченный запрос получает `continue()` или `abort()`, иначе страница зависает.
- Заблокированная навигация главного фрейма даёт `BLOCKED_ADDRESS`, заблокированный подресурс — счётчик `blockedRequests`; страница при этом замеряется.
- Node-пробы (http→https, robots, sitemap) идут через тот же guard, редиректы не следуют.

**Ожидание.**
- `goto` ждёт `domcontentloaded` с таймаутом до 15 с.
- Затем `load` ждётся мягко, до 8 с, в рамках общего бюджета.
- Если `load` не наступил, страница всё равно замеряется: `speed.loadTimedOut = true`, находка `load-timeout` (critical), скорость ограничена 30 баллами.
- `HTTP_ERROR` и статус берутся из главного ответа браузера.

**Бюджеты.**
- Быстрый путь: 25 с.
- Полный отчёт: 45 с.
- `maxDuration` маршрутов: 60 с.
- Одна повторная попытка при `DNS_FAILED`.

**Версии.**
- `Measurement.engineVersion = "2.0.0"`.
- Сравнивать сохранённые аудиты можно только в пределах одной версии движка.

**Радар.**
- `normalizeWebsite` берёт первый настоящий сайт из склеенного списка.
- Агрегаторы и конструкторы (Booking, Agoda, TripAdvisor, Google Sites, Taplink, 2GIS, Яндекс) не считаются сайтом компании.

## Последствия

- Медленные сайты получают оценку и главную находку вместо ошибки.
- Подресурсы с приватными адресами теперь блокируются (v1 их не проверял).
- **Остаточный риск — DNS rebinding.** Guard разрешает имя через node, а Chrome — заново, и между ними ответ DNS может смениться. Так было и в v1. Полное закрытие требует закрепления IP (proxy или `--host-resolver-rules`) и отложено. Риск ограничен: эндпоинт ничего не возвращает из ответа, кроме метрик.
- Старые строки `audits` не содержат `engineVersion` и `loadTimedOut`. Все читатели обязаны терпеть отсутствие этих полей.
