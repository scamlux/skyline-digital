# ADR 0002 — 3D-сцены (R3F) vs CSS-анимации

**Статус:** принято (временно, до решения владельца) · 2026-09

## Контекст

ТЗ §3 требует крупную 3D-сцену в hero главной, реагирующую на курсор/скролл, и 3D-акценты на карточках услуг и в переходах калькулятора — через React Three Fiber / drei. Одновременно §3 и §12 задают жёсткую границу: **LCP ≤ 2.5 с на мобильном 4G**, вес сцены ≤ 400 КБ, обязательный статичный фолбэк по `prefers-reduced-motion`. «Красивая сцена, которая роняет метрику, считается несделанной».

## Варианты

1. **Полноценный R3F в hero + акценты.** Максимально по §3. Риск: three+drei даже с ленивой загрузкой и code-split — сотни КБ JS; hero-canvas конкурирует за главный поток с LCP-элементом. Выполнимо в бюджет, но требует отдельной итерации с реальными замерами Lighthouse, а не «на глаз».
2. **CSS/Canvas-«псевдо-3D».** Sunrise-лоадер, пословный reveal, spotlight, параллакс-градиенты, живые превью проектов в «браузерной рамке». Нулевой JS-оверхед, LCP не страдает, reduced-motion тривиально уважается.
3. **Гибрид:** CSS сейчас, R3F точечно позже под замер.

## Решение

Пока — **вариант 2 (CSS)**, с явной фиксацией отклонения в [`../DESIGN-GAPS.md`](../DESIGN-GAPS.md). Причина: приоритет метрики запуска (§12) выше визуального «вау» на первой итерации; ввод R3F без инструментального замера LCP нарушил бы собственное правило ТЗ. Решение о вводе настоящего 3D оставлено владельцу — это визуально-бюджетный компромисс, а не чисто техническая развилка.

## Последствия

- Плюс: LCP под контролем, нет тяжёлого клиентского бандла, доступность бесплатна.
- Минус: формальное расхождение с §3 (R3F). Зафиксировано как открытый гэп.
- Обратимо: hero и карточки изолированы за компонентами — R3F-сцену можно вставить точечно позже (`dynamic(..., { ssr:false })`) без переписывания страниц.
